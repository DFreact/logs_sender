# Правила и тестовое событие

Ниже описан целевой контракт. Этап 6 реализован в версии 0.6.0:
[фактическое поведение, API и ограничения](routing-and-simulation.md).
Применение полей и подавление работают; отправка реализована в этапе 8,
эскалация — в этапе 9 ([контракт](event-actions-and-escalation.md)).
Сводки реализованы в этапе 10 ([контракт](digest-runtime.md)).
Сроки хранения событий ещё не настроены.

Определение источника и обработка — разные этапы и разные типы правил.
Источник первоначально может быть не определён, важность — не задана.
Общие условия — версионированное дерево данных, не выполняемый Python/SQL.

Поля: отправитель, получатели, тема, текст, заголовки, входной адаптер,
метаданные; после определения источника — источник, важность, категория,
тип и метки. Операторы: equals, not_equals, contains, not_contains,
starts_with, ends_with, regex, числовые сравнения; группы AND/OR/NOT.
Пустое значение отличается от отсутствующего поля. Проверка условий задаёт
тип, регистр, поведение для списков и null; неявных преобразований чисел нет.
Отрицание отсутствующего поля не должно неожиданно совпадать: использовать
явное условие exists. Регулярные выражения ограничить длиной и временем
либо выбрать движок без катастрофического возврата; выбор проверить на этапе.

В MVP ограничить вложенность тремя уровнями и размер дерева, например 100
условиями; ограничения сделать явными в API и UI. Конструктор показывает
«Когда», «И», «Или», «Не», «Тогда», «Отправитель», «содержит», «Установить
важность», «Отправить уведомление». Редактирование JSON пользователем не требуется.

Правила определения источника идут по priority ASC, затем id для стабильности.
Первое совпадение завершает этот этап и назначает источник, важность, категорию,
тип и метки. Правила обработки вычисляются по снимку результата этого этапа;
все совпадения фиксируются до применения действий, поэтому изменения одним
правилом не влияют на совпадение следующего. Для конфликтующих скалярных
назначений побеждает правило с наивысшим приоритетом, метки объединяются.
Подавление имеет приоритет над всеми действиями отправки; сохранить объяснение.

Действия: назначить поля, отправить сразу/с задержкой/по расписанию, включить
в сводку, подавить, запустить эскалацию. Ссылка на невидимый или выключенный
канал не предлагается при создании; сервер валидирует доступность отдельно.
Версия правила и снимок действий сохраняются. Эффекты защищены уникальным
ключом событие/правило/версия/действие; повторный запуск не создаёт копии.
Для действия «на каждое поступление» ключ дополнительно содержит occurrence_id.

Сохранение выполняет валидацию и создаёт неизменяемую RuleVersion с автором,
временем и аудитом. Конкурентное изменение проверяет ожидаемую version; конфликт
возвращает VERSION_CONFLICT. Просмотр истории входит в MVP, откат — будущий этап.

## Тестовое событие

POST /api/v1/rules/simulate принимает тестовые поля и возвращает объяснение:
совпавшее правило определения источника, источник, правила обработки, важность,
результат объединения повторов, эффективные сроки хранения, предполагаемые
уведомления. Симуляция использует тот же вычислитель с отключённым выполнением
эффектов: не обновляет счётчики, не создаёт задачи/эскалацию, не отправляет.
Результат сравнения с текущими данными является снимком, не гарантией будущего.

Отдельный POST /api/v1/notifications/test требует прав администратора,
явного действия «Отправить тестовое уведомление», выбранного канала и аудита.
Нельзя превратить симуляцию в реальную отправку случайным значением по умолчанию.
Объяснение содержит локализованные названия полей/действий, а не дерево API.

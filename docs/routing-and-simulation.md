# Правила обработки и тестовое событие

Реализованный контракт этапа 6, версия 0.6.0. Настройки и симуляция доступны
администратору. История обработки события доступна всем ролям с правом просмотра
этого события. Каналы добавлены в этапе 7, выполнение новых действий отправки — в этапе 8
([контракт доставки](notification-delivery.md)). Ниже описана базовая семантика этапа 6.

## Настройка правила

В разделе «Правила обработки» указать название, описание, приоритет, условия
и действия. Условия задаются тем же визуальным конструктором, что и при
определении источника. Дополнительно доступны источник, важность, категория,
тип события и метки. Источник выбирается по названию, важность — по русской
подписи; их внутренние значения не требуется вводить вручную.

До 100 правил на команду, включая выключенные; до 100 узлов в дереве условий,
глубина 0–3; до 10 действий в правиле. Поля источника и важности поддерживают
равенство, неравенство и наличие. Числовые сравнения применяются только к
дополнительным данным. Типы, отсутствие значений, регистр и RE2 соответствуют
[контракту определения источника](source-identification.md).

Действия:

| Действие | Поведение на этапе 6 |
| --- | --- |
| Установить поля | Применяет важность, категорию, тип; объединяет метки |
| Подавить уведомления | Устанавливает событию статус «Подавлено» и отменяет действия отправки |
| Подготовить уведомление | Сохраняет намерение: сразу, с задержкой или на указанное время |
| Включить в сводку | Сохраняет намерение включения в сводку |
| Запустить эскалацию | Сохраняет намерение запуска эскалации |

Установить поля можно одним действием на правило. Неуказанное значение
сохраняется; явно пустые категория и тип очищают соответствующее поле.
Метки добавляются к существующим без повторов, до 20 меток по 64 символа
в одном действии. Итоговый набор может быть больше набора одного правила.
Задержка API — 1–2 592 000 секунд; форма использует 1–43 200 целых минут.
Время запланированной отправки обязательно содержит часовой пояс; форма
переводит введённое время браузера в абсолютный момент.

Исторические намерения этапа 6 не являются уведомлениями или фоновыми задачами
и не отправляются автоматически после обновления. С этапа 8 новое действие
отправки с выбранным доступным каналом создаёт уведомление в той же транзакции.
Без выбранного канала оно остаётся намерением. С этапа 9 новое действие
эскалации с выбранной включённой политикой создаёт запуск и сроки шагов
для нового неподтверждённого события ([контракт](event-actions-and-escalation.md)).
С этапа 10 действие «Включить в сводку» назначает поступление выбранной сводке
с отбором по правилам ([контракт](digest-runtime.md)). Для учёта повторов нужна
область «Для каждого поступления». Симуляция по-прежнему не создаёт уведомлений.

## Порядок и конфликты

После определения источника сохраняется снимок нормализованных полей. По нему
вычисляются **все** совпадения правил обработки. Порядок — приоритет по
возрастанию, затем постоянный идентификатор. Изменения одного правила не
влияют на совпадение следующего.

Первое назначение скалярного поля побеждает; метки всех подходящих действий
объединяются. Решение сохраняет применённые и отклонённые из-за приоритета
поля. Подавление имеет приоритет над уведомлениями, сводками и эскалацией,
независимо от положения подавляющего правила в списке. Уже подавленное событие
остаётся подавленным и для действий на следующие поступления.

По умолчанию действие выполняется «Для нового события». При объединении
повтора такое действие получает результат «Пропущено для повтора», в том числе
если правило изменили после первого поступления. Явное «Для каждого поступления»
позволяет применять действие к повторам. Для такого назначения исходные значения
карточки сохраняются, если действие их не меняет; новые метки добавляются к уже
накопленным. Сам поиск повторов использует поля **до** правил обработки.

## Транзакции и история

Миграция `0006` добавляет `routing_rules` и `rule_executions`. `rule_versions`
получает второго допустимого владельца: правило определения источника или
правило обработки, строго один из них. Существующие версии сохраняются.

Каждое сохранение создаёт версию с автором, временем и снимком конфигурации;
конфликт ожидаемой версии возвращает 409. Изменения входят в журнал аудита.
Отключение сохраняет историю; удаления и отката версии через интерфейс нет.

Поступление, счётчик, изменения события, записи решений и завершение задачи
фиксируются одной транзакцией. При сбое откатываются вместе. Повтор задачи
защищён сохранённым поступлением, арендами и уникальностью эффекта:
событие / версия правила / индекс действия / область исполнения. Область —
событие для обычного действия, поступление для действия на каждое поступление
или записи о пропуске повтора. Повтор обработки уже записанных решений ничего
не применяет повторно. На карточке события есть раздел «Обработка события»
с русскими названиями действий и результатов, по 25 записей на страницу.

## Симуляция

«Тестовое событие» принимает поля проверяемого сообщения. Заголовки и
дополнительные данные вводятся строками формы; у дополнительных данных можно
выбрать текст, число, логическое значение или отсутствие значения.
Источник определяется правилами либо выбирается вручную. При ручном выборе
назначения правила определения источника не применяются, что явно показано
в результате. Это проверка заданных полей, а не повторный MIME-разбор файла.

Симуляция использует те же функции определения источника, вычисления ключа
повторов, проверки окна и разрешения конфликтов, что и реальная обработка.
Для неё отсутствуют операции создания ключей повторов и записей исполнения.
Не создаются события, исходные сообщения, задачи, уведомления или эскалации;
не меняются счётчики и журнал аудита. POST всё равно требует сеанса, CSRF
и прав администратора. Чтение согласовано с изменением конфигурации блокировкой
команды; результат поиска повторов остаётся предварительным снимком.

Результат показывает источник, применённую версию определения, итоговые поля,
статус, повтор либо новое событие и решения всех совпавших правил. Если для
неопределённого REST-источника нужен контекст ключа приёма, симуляция сообщает,
что повторы не проверены, и показывает план нового события. Секретный ключ
для тестового события вводить не требуется.

Срок хранения событий и исходных сообщений пока не настроен: возвращается
`NOT_CONFIGURED`, в интерфейсе показано отсутствие автоматического удаления.
Предложенные в архитектуре 90/30 дней не выдаются за уже действующую политику.
Настройка и применение сроков хранения относятся к этапу 11.

## API

| Путь с префиксом `/api/v1` | Назначение |
| --- | --- |
| `GET/POST /routing-rules` | Список и создание |
| `PATCH /routing-rules/{id}` | Изменение с ожидаемой версией |
| `GET /routing-rules/{id}/versions` | История с `offset` и `limit` |
| `POST /rules/validate` | Проверка конфигурации без сохранения |
| `POST /rules/simulate` | Симуляция сохранённых активных правил |
| `GET /events/{id}/processing` | Решения для события, `offset`, 25 записей |

Для воспроизведения проверок собранных образов:

```bash
python3 scripts/verify-identity.py --routing
```

Скрипт использует отдельный стенд: реальный SMTP и обработчик, проверки
PostgreSQL (включая параллельные поступления), все страницы через Nginx.
После завершения удаляет только свои временные данные.

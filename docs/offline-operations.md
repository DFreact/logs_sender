# Автономная установка и восстановление

Комплект `0.12.2-offline.1` содержит готовые образы приложения 0.12.2, PostgreSQL
и Redis, конфигурацию Compose, инструменты обслуживания и эту инструкцию.
Схема БД — `0012`. Перенос между архитектурами процессора не поддерживается:
платформа образов записана в `manifest.json`. Исходный код, Node.js и загрузка
пакетов при установке не нужны. Нужны Linux, Python 3.7+, Docker Engine и
Docker Compose v2 с поддержкой `--wait` и `--pull never`. Сам Docker и Python
устанавливаются средствами организации; их пакеты в комплект не входят.

## Подготовка комплекта

На машине сборки, после проверок образов:

```bash
python3 scripts/build-offline.py --output /защищённый/путь/комплект
```

Команда использует локальные образы из `infra/compose/compose.yaml` и ничего
не загружает. Каталог должен отсутствовать. Результат — каталог, который
переносят целиком. SHA-256 манифеста передают отдельно по доверенному каналу.
Контрольные суммы обнаруживают повреждение, но не заменяют цифровую подпись:
не запускайте инструменты из неизвестного комплекта. В комплект не включаются
секреты текущей установки, база, файлы сообщений и учётные записи.

## Установка без Интернета

Сначала сверить SHA-256 `manifest.json` с полученным от сборщика значением.
Далее из каталога комплекта:

```bash
python3 admin.py verify
python3 admin.py load
python3 preflight.py --output /tmp/eventhub-preflight.json
sudo python3 network-policy.py --project eventhub --subnet 172.31.54.0/24 \
  --output /srv/eventhub-policy
sudo python3 network-guard.py apply --policy /srv/eventhub-policy
sudo python3 admin.py install --directory /srv/eventhub --project eventhub \
  --http-port 8080 --smtp-port 2525 --subnet 172.31.54.0/24 --network-policy /srv/eventhub-policy
```

Установка не собирает образы и запрещает их загрузку из реестра. Создаются
случайные секреты; каталог установки имеет права 0700. Файлы секретов доступны
непривилегированным контейнерам через точечное монтирование и закрыты для других
пользователей узла приватным родительским каталогом. Не ослабляйте его права.
Существующий каталог, проект или тома не перезаписываются. При ошибке неполная
установка сохраняется для диагностики; команды запуска не считают её готовой.

Первого администратора создают с интерактивным скрытым вводом пароля:

```bash
docker compose -p eventhub --env-file /srv/eventhub/settings.env \
  -f /srv/eventhub/compose.json exec api python -m app.cli create-admin \
  --username admin --display-name 'Администратор'
```

HTTP и SMTP привязаны только к `127.0.0.1`; это локальная конфигурация установки.
Доступ пользователей из сети требует корпоративного HTTPS-прокси и согласованных
настроек доверенных прокси, допустимых адресов и защищённого SMTP. Открывать эти
порты наружу с текущими настройками нельзя считать готовой защищённой публикацией.
Параметры нагрузки находятся в `settings.env` установки. Сетевой профиль имеет приоритет над переменными разрешённых адресов.
Не помещайте туда пароли; секреты находятся в `.secrets`. Настройки оформления
сервера остаются в базе и восстанавливаются вместе с ней.

Команды запуска и остановки:

```bash
sudo python3 admin.py stop --directory /srv/eventhub
sudo python3 admin.py start --directory /srv/eventhub
```

`--isolated` при установке или восстановлении создаёт внутреннюю сеть Docker:
это режим стенда без внешней доставки. На проверенном Docker публикация портов
такой сети недоступна с узла; проверочные запросы выполняются внутри контейнеров.
Для обычного доступа к интерфейсу и рабочих внешних каналов этот флаг не задают.
Файлы комплектов и резервных копий сохраняйте отдельно от каталога установки.
Не меняйте образы и схему вручную: комплект проверяет идентификаторы образов.

## Согласованная резервная копия

```bash
sudo python3 admin.py backup --directory /srv/eventhub --output /backup/eventhub-2026-10-06
```

Каталог назначения должен отсутствовать. На всё время копирования останавливаются
приём, API и фоновые обработчики. После их остановки фиксируется точка копии;
PostgreSQL остаётся работающим. Создаются согласованные `database.dump`,
`blobs.tar.gz`, ключ расшифровки каналов и параметры установки. Redis не копируется:
источник задач — PostgreSQL. Проверяются каталог дампа, допустимые пути файлов
и чтение архива. Манифест с контрольными суммами записывается последним, после
синхронизации файлов на диск. Отсутствие манифеста означает незавершённую копию.

В блоке завершения возобновляется только работа компонентов, запущенных перед
копированием. При аварии узла или принудительном завершении процесса проверьте их
состояние вручную. Не запускайте другие экземпляры приложения, использующие эту
БД и хранилище, во время копирования: инструмент обслуживает один Compose-проект.
Параллельные команды обслуживания одного каталога блокируются файловой блокировкой.

Копия содержит конфиденциальные данные и ключи в открытом виде внутри защищённого
каталога. Размещайте её на зашифрованном носителе с ограниченным доступом;
шифрование архива и отправка на удалённый носитель в инструмент не входят.
Не храните единственную копию на диске сервера. Проверка контрольных сумм
не заменяет регулярного пробного восстановления.

## Восстановление в новую установку

Используйте тот же комплект и ту же архитектуру. Исходную установку команда
не изменяет. На том же узле требуются другие имя проекта, порты и подсеть.

```bash
python3 admin.py restore --backup /backup/eventhub-2026-10-06 \
  --directory /srv/eventhub-recovered --project eventhub-recovered \
  --http-port 8083 --smtp-port 2528 --subnet 172.31.55.0/24 --isolated
```

Сначала проверяются все контрольные суммы и совместимость. Дамп восстанавливается
одной транзакцией в новую БД. Архив извлекается потоково только в пустое хранилище;
ссылки и выход за пределы каталога запрещены. Проверяются каждый сохранённый файл
в состоянии готовности, его размер и SHA-256, а также расшифровка секретов каналов.
Ключ каналов сохраняется; ключ сеансов и пароли PostgreSQL/Redis создаются заново.
Сеансы пользователей удаляются: после восстановления нужно войти повторно.

После восстановления приём, API и обработчики остаются остановленными. Проверьте
адреса каналов и исключите одновременную отправку исходной и восстановленной
установками. Затем выполните `start --directory /srv/eventhub-recovered`.
Восстановленные задачи подхватят обработчики; незавершённые аренды восстанавливаются
по их срокам. Внешняя система могла принять уведомление после точки копии:
повторная доставка возможна. Защита от неё требует идемпотентности получателя.

## Ограничения и аварийные действия

RPO определяется возрастом последней завершённой копии. Изменения после её точки
не восстанавливаются. Это не непрерывное архивирование журнала PostgreSQL и не
восстановление на произвольный момент. RTO зависит от размера базы и файлов,
скорости диска, времени проверки всех файлов и истечения аренд. Измерение на
контрольном наборе приводится в отчёте этапа 12; оно не является нормативом для
больших архивов. Простои копирования также растут вместе с объёмом данных.

При повреждённой копии используйте предыдущую проверенную. При нехватке места
не удаляйте рабочие тома: освободите место вне них или выделите новый диск.
Не применяйте `down -v` к рабочей установке. Автоматического обновления поверх
существующих данных и отката версии этот комплект не выполняет. Для обновления
нужны отдельная проверенная миграция и копия; восстановление старой копии потеряет
последующие изменения. Изоляция данных разных компаний пока не реализована.

## Ограничение исходящей сети

Комплект является кандидатом для приёмки. Открытые замечания безопасности —
в `docs/security-review.md` исходного проекта. Установка в новый каталог
не меняет сетевую политику других работающих установок.

Пример выше создаёт профиль **без разрешённых внешних адресов**: MAX выключен,
никакой Интернет контейнерам не разрешён. Наличие токена не требуется.
Для включения MAX перед созданием установки добавьте к `network-policy.py`
один или несколько `--max-ip` с точными IPv4, согласованными для
`platform-api2.max.ru`. Не подставляйте произвольный публичный адрес, подсеть,
старый домен или IP из примеров тестов. Список должен подтвердить сетевой администратор;
генератор не подтверждает принадлежность IP оператору MAX. DNS-запросы наружу запрещены,
имя фиксируется в контейнерах. При смене адресов нужен новый проверенный профиль.

Только API (проверка бота) и обработчик отправки могут обратиться к разрешённым
IP по TCP/443. Прочие соединения за пределы сети проекта, новые соединения к узлу,
внешний DNS и IPv6 блокируются. Связь контейнеров друг с другом и ответы на
входящие подключения сохраняются. Telegram и внешние HTTP-каналы выключены.
Этот строгий профиль также не разрешает исходящий SMTP в корпоративную сеть;
его расширение требует отдельных узких правил и проверки, а не `0.0.0.0/0`.

Правила применяются в отдельной таблице nftables, без очистки чужих таблиц.
Нужны локальный обычный Docker Engine и права администратора узла. Удалённый
Docker и режим rootless не поддерживаются защитным профилем. На Astra дополнительно
проверяются совместимость nftables с установленным Docker и действующие мандатные
ограничения. `preflight.py` не заменяет такую приёмку.

До каждого запуска инструмент сверяет действующие правила и контрольную сумму
Compose. Изменённая или отсутствующая защита запрещает запуск. У контейнеров
защитного профиля выключен автоматический перезапуск: после перезагрузки узла
сначала выполнить `network-guard.py apply`, затем `admin.py start` от администратора.
Не запускать Compose вручную в обход проверки. Системная служба запуска и контроль
сохранности правил во время работы должны быть настроены эксплуатацией.
Удаление правил после запуска привилегированным администратором не останавливает
уже работающие контейнеры автоматически. Для защиты от этого нужна независимая
политика исходящего доступа на сетевом периметре.

Фильтр относится к сети данного проекта, а не к другим контейнерам и программам
узла. Обновления ОС, NTP, DNS самого узла, Docker и прочий служебный трафик
ограничиваются политикой организации. Подготовка зависимостей и аудит OSV выполняются
на отдельной машине с Интернетом; в комплекте нет фонового обновления или отправки
телеметрии. При установке используются `--pull never`, при автономной сборке —
`--pull=false --network=none --no-cache` с локальными образами зависимостей.

Для доверенного центра сертификации MAX передать при `install` или `restore`
`--ca-file /защищённый/путь/approved-ca.pem`. Использовать проверенный организацией
PEM-набор корневых сертификатов, полученный заранее по доверенному каналу.
Он копируется в установку, монтируется только для API и отправки и проверяется
по контрольной сумме перед запуском. Закрытые ключи здесь недопустимы. Проверка
сертификата и имени сервера никогда не отключается. Сертификаты и сетевой профиль
не входят в резервную копию: на новом узле их предоставляют заново.

Синтаксис инструментов обслуживания проверен на совместимость с Python 3.7;
фактический прогон выполнен на Python 3.14 под Ubuntu, не на Astra.
Матрица реальной приёмки — `docs/astra-linux.md` исходного проекта.

## Разделение прав в 0.12.2

Приложение работает под отдельной ролью PostgreSQL с доступом к данным.
Суперпользователь используется только первоначальной настройкой и обслуживанием
из контейнера PostgreSQL. Миграции и восстановление выполняются другой ролью,
без административных прав кластера. Подробности — `database-privileges.md` в комплекте.
Установка создаёт шесть независимых секретов. При восстановлении сохраняется
только ключ каналов; все остальные ключи и пароли создаются заново.
Дамп восстанавливается в новую БД с новым владельцем объектов; после этого
права существующих и будущих объектов выдаются заново. Приложение не получает
прав изменения схемы или таблицы версии миграций.

Не заменяйте Compose поверх старой установки: новый комплект не выполняет
автоматическое преобразование владельцев и обновление старых копий.

## Перенос старого локального стенда

Комплект 0.12.2 дополнительно содержит `upgrade.py` для явного перехода
копии 0.11.0/0011 в новую установку 0.12.2/0012. Обычная команда `restore`
по-прежнему принимает только копию своей версии. Перенос в существующие тома
не поддерживается. Перед рабочим переключением обязательно пробное восстановление.
Описание процедуры и локального доступа — `docs/local-upgrade.md` в репозитории.

В 0.12.2 у изолированной установки закреплены адреса веб-сервера и SMTP,
динамические адреса вынесены во вторую половину подсети. Порты Docker в таком
режиме не публикуются. Пользовательские сокеты systemd используются только
локальным Ubuntu-стендом и не заменяют промышленный сетевой профиль.

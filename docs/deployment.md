# Развёртывание и эксплуатация

Этот документ описывает целевое развёртывание. Для реализованных этапов 1–4
используются PostgreSQL, Redis, API, Nginx, SMTP-приёмник, обработчики служебных
и входящих задач, диспетчер и планировщик;
команды и ограничения — в [local-development.md](local-development.md).

Docker Compose: nginx, api, smtp-receiver, dispatcher, scheduler,
processing-worker, delivery-worker, maintenance-worker, postgres и redis.
Разные обработчики могут использовать один образ с разными командами.
Миграции выполняются отдельной одноразовой командой до запуска новой версии.

Наружу публикуются только HTTPS и необходимый SMTP-порт. PostgreSQL и Redis
доступны лишь во внутренней сети. Тома: PostgreSQL, Redis, исходные сообщения,
вложения и ограниченные журналы. Redis с сохранением на диск улучшает
восстановление, но истинное состояние задач остаётся в PostgreSQL.
Рабочие процессы запускаются без root; непривилегированный SMTP-порт контейнера
можно отобразить на необходимый порт узла.

Изолированная установка получает архив фиксированных образов, локальные
ресурсы frontend, миграции, конфигурационный шаблон без секретов и инструкции.
Сборка и проверка зависимостей выполняются до переноса; runtime ничего
не скачивает. Telegram и внешний Webhook работают только при явно разрешённой
связи; отсутствие Интернета не препятствует работе локального приложения.

## Состояние системы

/health/live проверяет жизнь процесса без обязательной доступности БД.
/health/ready отражает готовность обслуживать соответствующую роль процесса,
включая БД и хранилище. Недоступность Redis показывать как ограничение обработки;
приём может оставаться готовым, пока надёжно сохраняет данные в БД и имеет место.
/metrics доступен только доверенной сети/системе сбора.

Контролировать PostgreSQL, Redis, возраст heartbeat обработчиков, задержку
планировщика, SMTP-приёмник, доступность Nginx и каналов. Метрики: события и
уведомления в минуту, размер/возраст очереди, неуспешные задачи, неотправленные
уведомления, CPU, память и диск. Называть границы метрик: ресурсы контейнера
не выдавать за ресурсы всего узла. Состояние контейнеров — только через отдельно
разрешённый ограниченный источник; не монтировать Docker socket в приложение.
Нет данных → «Нет данных», а не ложное «Работает».

Обзор показывает события за день, критические и неподтверждённые события,
очередь, ошибки отправки, частые источники/повторы и состояние хранения.
Коды компонентов преобразуются в русские подписи, не раскрывают внутренние
имена контейнеров. Порог свободного места ограничивает новый приём до
исчерпания диска с временной ошибкой, сохраняя уже подтверждённые данные.

## Резервное копирование и обновление

Копировать согласованный набор БД и blob, конфигурацию и отдельно защищённые
ключи. До внедрения задать RPO/RTO и периодичность; проверить восстановление
на отдельной установке. На время резервного копирования замораживать удаление
blob либо применять согласованные снимки, чтобы ссылки БД оставались валидны.
При восстановлении сначала БД/blob/секреты, затем миграции совместимой версии,
проверка состояния и восстановление незавершённых WorkItem. Redis можно
восстановить из БД. Возможные повторные внешние отправки разбирать по истории.

Перед обновлением — проверенная резервная копия и совместимость схемы.
Откат приложения возможен только с совместимой схемой; обратимость миграций
не предполагается автоматически. Выпуск включает проверку русского языка
и безопасных ошибок, в том числе статической страницы Nginx.

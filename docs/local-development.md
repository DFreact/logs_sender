# Локальная разработка: запуск и проверка

## Что реализовано

Этапы 1–4: React/TypeScript/Vite, FastAPI, безопасные ошибки, PostgreSQL,
SQLAlchemy/Alembic, Nginx и Docker Compose. Есть вход/выход, смена пароля,
пользователи, серверные права и журнал аудита. Миграция `0002_identity` создаёт
`teams`, `users`, `memberships`, `sessions`, `login_limits`, `audit_entries`.
Учётные записи миграции не создают. Миграция `0003_background` добавляет
`work_items`, `blobs`, `storage_scans`, `component_heartbeats`. Работают Redis,
Dramatiq, отдельные диспетчер и планировщик, файловое хранилище и начальная
страница «Состояние системы». Миграция `0004` добавляет приём и события;
работают SMTP-приёмник, отдельный обработчик нормализации и раздел «События».
Контракт приёма — [ingestion.md](ingestion.md). Контракты — в [background-processing.md](background-processing.md).
`/health/live` проверяет только доступность процесса, независимо от БД.

Все интерфейсные тексты — в `frontend/src/i18n/locales/ru/messages.json`.
Компоненты используют `useI18n()`. Серверные перечисления генерируются в
`frontend/src/api/generated.ts`, таблицы переводов проверяются TypeScript.
Страницы Nginx и начальная страница при неудачной загрузке JavaScript
генерируются из того же каталога во время сборки. Клиент отбрасывает неизвестные
коды, параметры и технические подробности ошибок. Поля ошибок проходят белый список и отображаются русскими подписями.
Тексты локальной команды администратора — в `backend/app/i18n/cli.ru.json`.

## Каналы и шаблоны

Этап 7 добавляет страницы «Каналы уведомлений» и «Шаблоны», настройки выходных
адаптеров, проверку подключения и предпросмотр. Текущая версия — 0.12.2,
миграция — `0012`. Этап 8 добавляет очередь доставки, попытки, повторы и отмену
([контракт](notification-delivery.md)). [Настройка исходящих подключений и ограничения](channels-and-templates.md).
Этап 9 добавляет подтверждение, решение и подавление событий, политики эскалации
с историей версий и сохранёнными сроками шагов ([контракт](event-actions-and-escalation.md)).
Этап 10 добавляет ежедневные сводки, контроль готовности поступлений,
предпросмотр и историю состава ([контракт](digest-runtime.md)).
Для проверки отдельного стенда: `python3 scripts/verify-identity.py --background --ingestion --routing --channels --escalations --digests`.
Флаг `--digests` добавляет локальную отправку одной почтовой сводки с повторными
поступлениями, проверки календарных границ и браузерные сценарии всех ролей.
Флаг `--escalations` включает проверки доставки и добавляет сроки 0/10/30 минут
с управляемыми часами, конкурентное подтверждение и браузерные действия с событиями.
Для повторной проверки интерфейса после успешного серверного прогона добавить
`--browser-only`: временный стенд и выбранные тестовые данные создаются заново,
серверный pytest пропускается, браузерный набор выполняется полностью.
Это не заменяет полный прогон перед приёмкой изменений серверного кода.
Ключ `.local/secrets/channel_secret` создаётся командой инициализации и требует
отдельной защищённой резервной копии. Без него нельзя восстановить секреты каналов.

## Docker Compose

Проверено с Python 3.14.4, Node.js 22.22.1, PostgreSQL 16.15, Redis 8.2.10 и Dramatiq 2.2.0. Образы основы
зафиксированы по версии и digest; Python-пакеты — полным списком версий,
JavaScript-зависимости — `package-lock.json`. Обновлять фиксацию осознанно,
после проверок. Нижняя версия Python проекта — 3.12, но отдельная проверка
этой версии в текущем этапе не выполнялась.

Из корня репозитория:

```bash
python3 scripts/init-local.py
docker compose -p eventhub-dev -f infra/compose/compose.yaml up -d --build --wait
docker compose -p eventhub-dev -f infra/compose/compose.yaml ps
```

Адрес: http://127.0.0.1:8080. API, БД и Redis наружу не публикуются. Контейнеры
работают без root, с файловой системой только для чтения, отдельными томами/
временными каталогами, без дополнительных capabilities и с ограничением журналов.
Секреты генерируются локально и исключены из контекста сборки. На узле каталог
секретов имеет права 0700; файлы доступны непривилегированным процессам
через точечное монтирование Compose. Не публиковать эти файлы.

Служба `storage-init` создаёт каталоги в общем томе `blobs` с владельцем 10001.
API и обработчик используют один и тот же том. Redis запускается с паролем,
128 МиБ памяти и без удаления ключей при заполнении; сохранение очереди на диск
не требуется для сохранности задач, поскольку их источником остаётся PostgreSQL.
Фоновые процессы автоматически перезапускаются, после явного `stop` остаются
остановленными. Сигнал готовности можно проверить через `/health/ready`.
Подробности доступны администратору на странице «Состояние системы».

Опциональные параметры заданы в `.env.example`. Например, после создания
`.env` запуск с ними:

```bash
docker compose -p eventhub-dev -f infra/compose/compose.yaml --env-file .env up -d --build --wait
```

`HUB_TIME_ZONE` задаётся при сборке интерфейса. В интерфейсе отображается
русское название часового пояса, в конфигурации используется IANA-идентификатор.
Изменение этой настройки требует пересборки. Настройки профиля появятся позже.

Остановка с сохранением данных:

```bash
docker compose -p eventhub-dev -f infra/compose/compose.yaml stop
```

Первого администратора создать в интерактивном терминале:

```bash
docker compose -p eventhub-dev -f infra/compose/compose.yaml exec api python -m app.cli create-admin --username admin --display-name 'Администратор'
```

Пароль от 12 до 128 символов вводится дважды без отображения. Не передавать его
аргументом или через переменную командной строки. Команда откажет после первого
создания. Затем открыть страницу входа; новые учётные записи и роли доступны
администратору в разделе «Пользователи». Отключение, смена роли или пароля
завершают сеансы затронутого пользователя. Последнего администратора нельзя
отключить или понизить в правах. Удаления пользователей нет, история сохраняется.

Сеанс действует 8 часов. По умолчанию требуется HTTPS, cookie имеют Secure,
HttpOnly и SameSite=Strict. Compose явно разрешает HTTP только для localhost/
loopback, порт публикуется на 127.0.0.1. Для корпоративной сети необходимы TLS,
точный список HTTPS-origin и отключение `HUB_ALLOW_INSECURE_LOCAL_HTTP`.
Локальный стенд не является готовой производственной поставкой. Роли БД
для приложения и миграций разделены; правила описаны в [модели прав](database-privileges.md).

Подсеть стенда по умолчанию `172.31.51.0/24`. При конфликте задайте свободную
`HUB_DOCKER_SUBNET` в `.env`. Nginx перезаписывает адрес клиента, backend доверяет
ему только из этой сети. После изменения подсети пересоздайте контейнеры через
`up -d --force-recreate --wait`; том БД сохраняется. Не добавляйте в доверенные
прокси все адреса сети организации.

## Разработка без пересборки контейнеров

Backend из корня:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements-dev.txt
.venv/bin/uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000 --no-access-log
```

Frontend в другом терминале:

```bash
cd frontend
npm ci
npm run dev
```

Vite направляет `/health/` и `/api/` на 127.0.0.1:8000. Для входа нужна БД с применёнными миграциями и созданным администратором.
Указать `HUB_DB_*`, `HUB_AUTH_SECRET_FILE`, `HUB_ALLOWED_ORIGINS` в окружении;
`.env` backend автоматически не загружает. Для Vite на локальном HTTP явно
задать `HUB_ALLOW_INSECURE_LOCAL_HTTP=true` и
`HUB_ALLOWED_ORIGINS='["http://127.0.0.1:5173"]'`; открывать именно этот адрес.
Порт БД Compose наружу не опубликован: для отдельного backend нужна отдельная
БД разработки. Для фоновых процессов также нужны `HUB_REDIS_HOST`,
`HUB_REDIS_PASSWORD_FILE`, общий `HUB_STORAGE_ROOT` и миграции.
Из `backend/` один раз выполнить `../.venv/bin/python -m app.storage.initialize`,
затем в отдельных терминалах запустить `../.venv/bin/python -m app.workers.runtime scheduler`
и такие же команды с `dispatcher` и `worker` вместо `scheduler`, с тем же окружением. Автоматические тесты поднимают собственные
изолированные данные.

## Проверки

Из корня:

```bash
.venv/bin/python scripts/generate-api-types.py --check
.venv/bin/ruff check --config backend/pyproject.toml backend scripts
```

Из `backend/`:

```bash
../.venv/bin/pytest -q
```

Из `frontend/`:

```bash
npm run build
npm test
npm exec playwright install chromium
npm run test:e2e
```

Браузерная проверка самостоятельно поднимает временную SQLite БД и серверы
на 8000/4173. Случайные тестовые пароли хранятся в `.local/e2e-credentials.json`
с правами 0600; файл удаляется после завершения сервера. Трассировки браузера
отключены, чтобы не сохранять пароли и cookie. Для проверки собранных образов
на настоящем PostgreSQL из корня:

```bash
python3 scripts/verify-identity.py --routing
```

Скрипт создаёт уникальный отдельный проект Compose, временный том и тестовые
учётные записи. С флагом `--background` останавливает и перезапускает только
временные Redis/обработчики, проверяет восстановление задач, аренды и отказ
файловой записи. Флаг `--sources` добавляет источники, версии правил,
границы окна и 20 конкурентных поступлений. Тестовые события для браузерных
проверок готовятся при любом наборе флагов. Флаг `--ingestion` добавляет реальные проверки SMTP/REST и отказов.
Флаг `--routing` включает проверки источников и правил обработки, запрет записи
при симуляции, конкурентное исполнение и реальный путь SMTP через фоновый процесс.
Для полного набора можно совместить `--background --ingestion --routing`. Без флагов остаются проверки
пользователей и всех страниц в браузере.
Запускает серверные проверки в отдельных схемах PostgreSQL
и браузерные — через Nginx, затем удаляет только свой стенд и временные данные.
Рабочая БД не изменяется. Нужны заранее собранные образы, `.venv`, зависимости
frontend и Chromium. По умолчанию используются порты 8081/55439 и подсеть
172.31.52.0/24; переопределения: `HUB_VERIFY_HTTP_PORT`, `HUB_VERIFY_DB_PORT`,
`HUB_VERIFY_SUBNET`. Тестовые лимиты входа повышены только на временном стенде;
проверки конкурентного ограничения используют собственный малый лимит.
Не запускайте тесты управления пользователями против рабочей установки.

Проверка инфраструктуры из корня:

```bash
python3 scripts/verify-local.py --exercise-outage
```

Команда проверяет русский ответ 404, контракт ошибок API и превышения размера,
заголовки безопасности, непривилегированные процессы, конфигурацию Nginx
и цикл миграции PostgreSQL. Для миграции создаётся временная схема в транзакции,
которая полностью откатывается; таблицы рабочего стенда не изменяются.
Флаг `--exercise-outage` кратко останавливает только API текущего стенда,
проверяет безопасный ответ прокси, затем запускает API в блоке `finally`.
Без флага проверка не останавливает контейнеры. При другом порте передать
`--base-url http://127.0.0.1:ПОРТ`.

В браузере проверяются источники, условия и история обоих видов правил,
тестовое событие, события,
состояние системы и очередь, ограничения доступа,
вход/выход, управление пользователями и паролем, аудит, обычный запуск, отсутствие внешних запросов, мобильная
ширина, обрыв сети/восстановление, некорректный JSON/HTML, неизвестный код,
сбой отображения и неудачная загрузка модуля. Снимки экрана сохраняются в `frontend/test-results/`, исключённом из репозитория.

`npm run check` проверяет типы и типичные непереведённые строки в JSX,
пользовательских атрибутах и уведомлениях. Этот анализ не доказывает отсутствие
всех возможных косвенных строк: ручная проверка новых экранов остаётся обязательной.

## Добавление текста или статуса

1. Проверить и при необходимости дополнить `docs/ui-language.md`.
2. Добавить ключ в русский каталог. Не импортировать каталог в компонент.
3. Использовать `t(key, params)`; для чисел/дат/количеств — форматтеры контекста.
4. После изменения backend enum запустить `.venv/bin/python scripts/generate-api-types.py`.
5. Дополнить явное отображение в `mappings.ts` и проверить безопасный вариант
   для неизвестного значения. `satisfies Record<Enum, TranslationKey>` блокирует
   пропущенный известный статус при сборке.

Добавление другого языка позднее: каталог с тем же набором ключей и параметров,
запись в реестре локалей и выбор контекста. В MVP реестр содержит только `ru`,
переключателя языка нет. Проверка использует тестовую локаль только внутри теста,
не добавляя её в поставку.

## Источники технических контрактов

Обработка ошибок опирается на [механизм обработчиков FastAPI](https://fastapi.tiangolo.com/tutorial/handling-errors/),
но пользовательские ответы формируются собственным безопасным контрактом.
Подключение миграций использует [контекст Alembic](https://alembic.sqlalchemy.org/en/latest/api/runtime.html).
Требования к среде сборки приведены в [документации Vite](https://vite.dev/guide/).

План автономной поставки готовых образов и дальнейшего развёртывания —
[deployment.md](deployment.md). Сборка этого этапа требует доступа к реестрам;
в рабочем приложении сетевых зависимостей от внешних ресурсов нет.


## Приём событий (этап 4)

Добавлены процессы `smtp` и `ingestion`, миграция `0004`, раздел «События».
К локальному SMTP можно подключаться на `127.0.0.1:2525`, получатель —
`events@localhost`. REST — `POST /api/v1/ingest`, требуется отдельный ключ приёма.
[Создание и отзыв ключей, протоколы, ограничения и TLS](ingestion.md).
Пользовательский сеанс не заменяет ключ приёма; ключ не даёт права читать события.

Проверка полного стенда с остановками БД/Redis, отказом диска, конкурентными
запросами и браузером (создаётся отдельный проект, его данные удаляются в конце):

```bash
python3 scripts/verify-identity.py --background --ingestion
```

Используются временные порты 8081, 2526, 55439 и подсеть 172.31.52.0/24.
Переопределение: `HUB_VERIFY_HTTP_PORT`, `HUB_VERIFY_SMTP_PORT`,
`HUB_VERIFY_DB_PORT`, `HUB_VERIFY_SUBNET`. Основной стенд не останавливается.

Обновление для больших архивов: [контракт и отдельный нагрузочный стенд](high-load.md).
Миграция индексов требует окна обслуживания и расширения PostgreSQL `pg_trgm`.

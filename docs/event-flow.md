# Полный поток обработки: четыре сценария

Общий путь: устойчивый приём → исходное сообщение → нормализация → определение
источника → объединение повторов → правила обработки → подготовка уведомления
→ задача → выходной адаптер → запись попытки. Каждая граница повторного
исполнения защищается сохранённым идентификатором. Сроки хранения назначаются
после определения источника; до этого действует глобальная политика.

## 1. Письмо Kaspersky → Telegram сразу

1. SMTP принимает письмо, сохраняет MIME, RawMessage и задачу; подтверждает приём.
2. Обработчик извлекает отправителя, тему и тело. Правило определения источника
   назначает «Kaspersky»; отсутствие совпадения оставило бы источник неопределённым.
3. Объединение повторов создаёт Event и первое EventOccurrence.
4. Правило обработки совпадает с источником/текстом, назначает важность и
   действие немедленной отправки. Сохраняются версия правила и ключ эффекта.
5. Шаблон формирует безопасное сообщение; Notification получает PENDING.
6. Обработчик отправки фиксирует PROCESSING и DeliveryAttempt, вызывает Telegram.
   Успех фиксирует SENT; ошибка — RETRYING или FAILED по общей политике.
7. UI показывает «Новое» и «Отправлено» либо русскую причину ошибки с действием.

## 2. Двадцать одинаковых писем за десять минут

1. Каждое письмо сохраняется отдельно с временем приёма и исходными данными.
2. Нормализация и определение источника дают одинаковые сравниваемые поля.
3. Блокировка DedupKey сериализует конкурентные поступления внутри фиксированного
   окна. Получаются одно Event, 20 EventOccurrence и occurrence_count = 20.
4. Только первое поступление создаёт обычное уведомление. Остальные обновляют
   последнее время; исходящие повторы доставки не считаются новыми событиями.
5. Пользователь видит счётчик «20 поступлений» и историю. Письмо ровно на правой
   границе окна образует новое событие. Повтор фонового задания счётчик не увеличивает.

## 3. Сообщения межсетевого экрана → сводка по почте в 08:00

1. Входной SMTP или REST сохраняет сообщения; правило определяет источник.
2. После объединения повторов правило включает поступления в ежедневную сводку,
   не создавая немедленных отправок.
3. В 08:00 выбранного часового пояса планировщик фиксирует календарное окно
   предыдущие 08:00 → текущие 08:00. Проверяется завершённость обработки приёма.
4. Обработчик фиксирует состав, считает поступления, группы и повторяющиеся
   события; формирует тему и тело по шаблону сводки.
5. Создаётся одно уведомление на канал. SMTP отправляет его через общую историю
   попыток. Рестарт планировщика не создаёт повторный запуск того же окна.

## 4. Критическое событие без подтверждения → эскалация

1. Событие проходит общий путь; правило назначает CRITICAL и запускает политику.
2. В одной транзакции создаются запуск эскалации, первый шаг и Telegram-уведомление.
3. Если пользователь подтвердил событие, фиксируются автор/время, оставшиеся
   шаги прекращаются. UI показывает «Подтверждено».
4. Иначе через 10 минут планировщик проверяет событие и создаёт почтовое
   уведомление службе безопасности с уникальным ключом шага.
5. Через 30 минут от начала при отсутствии подтверждения создаётся уведомление
   администратору. Сбой и рестарт между шагами не сбрасывают сроки.
6. Ошибки доставки каждого шага обрабатываются независимо. Уже начатую внешнюю
   отправку подтверждение не может гарантированно отменить.

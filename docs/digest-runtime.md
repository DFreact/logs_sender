# Сводки: контракт этапа 10

## Настройка и отбор

Раздел «Сводки» доступен всем трём ролям. Администратор создаёт и изменяет
настройки, выбирает канал и совместимый шаблон. Только администратор может
продлить ожидание или разрешить неполную сводку. Сервер проверяет права,
принадлежность команде, версию и защиту запроса независимо от интерфейса.

До 100 определений на команду. Поддерживается ежедневное расписание с точностью
до минуты, часовой пояс IANA, два режима периода и выбор источников/важности.
Время в форме вводится как «ЧЧ:ММ» в 24-часовом формате, независимо от языка браузера.
Пустые списки фильтров означают все значения. В форме доступны Москва,
Калининград, Екатеринбург, Новосибирск, Владивосток, Берлин и всемирное
координированное время. API принимает остальные установленные часовые пояса;
сохранённое значение форма сохраняет, не выдавая технический идентификатор
за пользовательскую подпись.

Режим «По источнику и важности» выбирает все подходящие поступления периода.
Режим «По правилам обработки» дополнительно требует нового решения
«Включить в сводку» с выбранной сводкой. Для учёта каждого повторного поступления
в правиле нужна область «Для каждого поступления». Несколько подходящих правил
не удваивают одно поступление. Старые намерения не исполняются задним числом.

Для каждого нормализованного поступления сохраняется отдельный снимок источника,
важности после правил, темы, подавления и назначенных сводок. Агрегаты не зависят
от последующих изменений важности события, названия источника или накопленного
счётчика события. Подавленные поступления не включаются; ручное подавление
до фиксации готового содержимого также исключает событие из состава.
Готовое сводное уведомление относится к нескольким событиям: последующее
подтверждение отдельного события не изменяет уже подготовленное письмо.

## Периоды и версии

Окно имеет границы `[начало, конец)`. Первый период начинается с создания
сводки: исторические поступления до этого момента не включаются.

- «Между плановыми запусками»: от предыдущей границы до текущего местного
  времени запуска. При переводе часов продолжительность может быть 23 или 25 часов.
- «Последние 24 часа»: ровно 24 часа перед границей, кроме сокращённого первого
  периода. При переходах местного времени возможны перекрытие либо промежуток
  между окнами; это объясняется в форме. Для непрерывного покрытия нужен
  режим между плановыми запусками.

Несуществующее местное время заменяется ближайшей доступной минутой.
Повторяющееся время используется один раз, в первом вхождении.
Перезапуск не начинает новый отсчёт: сохранены начало, следующая граница
и снимок настроек текущего периода.

Изменение настроек, включая выключение, действует со следующего периода.
Текущий период завершается с прежними настройками. Каждое изменение имеет
неизменяемую версию с автором и временем. Если есть пропущенные периоды,
сначала планировщик фиксирует их; API изменения просит дождаться этого,
чтобы новые настройки не применились задним числом.

За один проход планировщика выбирается не более десяти определений,
создаётся до восьми окон каждого. Для выключенного периода сохраняется
«Пропущено: сводка выключена», без уведомления. Уникальная пара границ
внутри определения и блокировка строки исключают двойной запуск.

## Контроль готовности и неполные сводки

Время приёма исходного сообщения назначается часами БД под разделяемой
блокировкой команды перед фиксацией. Нормализация берёт ту же блокировку.
Фиксация окна и контрольной отметки состава используют исключительную
блокировку команды. Поэтому ещё не завершившаяся транзакция приёма либо
нормализации не может остаться незамеченной при закрытии состава.

Пока в пределах окна есть необработанные исходные сообщения команды,
запуск показывает «Ожидает обработки поступлений». Проверяются все поступления
команды: до определения источника нельзя безопасно исключить их фильтром.
Исчерпание попыток нормализации не превращает такое сообщение в пустой период.

Срок ожидания настраивается от одной минуты до семи дней, по умолчанию час,
от границы окна. После него — «Требуется решение». Автоматической неполной
отправки нет. Если обработка завершится, подготовка продолжится автоматически.
Администратор может:

- продолжить ожидание ещё на настроенный срок;
- явно разрешить неполную сводку через диалог с последствиями.

Для неполной сводки сохраняются время отсечения и исходное число необработанных
поступлений. В состав попадают только результаты до этой отметки. Поздние
подходящие результаты показаны отдельным счётчиком и списком со ссылками
на события. Они не добавляются в уже отправленное письмо автоматически
и не выдаются за включённые в него. Неполнота указана в истории и готовом тексте.
Правило «не отправлять пустую сводку» действует и при явно разрешённой неполноте.

Решение содержит UUID операции и ожидаемую версию. Повтор последней операции
с тем же автором и параметрами не повторяет аудит. Несовместимые параметры,
устаревшая версия или уже завершённая подготовка возвращают безопасный конфликт.
Действия отправки через сетевой сбой не повторяются с новым ключом автоматически.

## Подготовка и доставка

Состав фиксируется в PostgreSQL пакетами до 200 подходящих поступлений.
В версии 0.10.1 порядок — время поступления и идентификатор, с составным индексом.
Сохранённый указатель и состав обновляются одной транзакцией. При сбое пакет
откатывается; следующий проход продолжает с сохранённого места. Ожидающие
запуски чередуются по времени последней проверки, чтобы не блокировать
готовые последующие периоды. Подготовку выполняет существующий планировщик;
отдельной сетевой отправки из него нет.

Итоги: число поступлений и отдельных событий, первое и последнее поступление,
группы по источникам и важности, 20 наиболее частых событий. В итоговом тексте
перечисляются до 20 наиболее частых источников; общие счётчики учитывают весь
состав. Полный состав доступен страницами по 25 поступлений.

После окончания состава агрегаты, готовое содержимое, одно уведомление
и задача доставки фиксируются вместе. Пустой период по умолчанию получает
«Пустой период» без отправки. При включённом «Отправлять пустую сводку»
создаётся уведомление с нулевыми счётчиками.

Для шаблона используются существующие безопасные переменные: `event.subject`
содержит название сводки, `event.body` — русский итоговый текст. Остальные поля
пусты. Разметка шаблона по-прежнему ограничена песочницей этапа 7. Выбранный
шаблон может отличаться от шаблона канала. Его версия и параметры канала
фиксируются при создании уведомления; изменения после подготовки его не меняют.
Общие ограничения размера и каналов действуют также для сводок: например,
длинная сводка для Telegram может завершиться понятной ошибкой шаблона.

Доставка идёт через общую очередь, историю попыток и повторы этапа 8.
«Уведомление создано» не означает успешную доставку: её статус и ссылка
показаны отдельно. Неопределённый сетевой результат сохраняет риск повторного
получения; гарантии единственного получения внешним почтовым сервером нет.

## API и хранение

Пути с префиксом `/api/v1/digests`:

| Путь | Назначение |
| --- | --- |
| `GET/POST /` | Чтение и создание определений |
| `PATCH /{id}` | Изменение ожидаемой версии |
| `GET /{id}/versions` | История версий, по 25 записей |
| `GET /{id}/preview` | Текущий состав: точные счётчики и первые 25 поступлений |
| `GET /{id}/runs` | История запусков, по 25 записей |
| `GET /runs/{id}/items` | Состав, `late=true` — поздние результаты |
| `POST /runs/{id}/wait` | Продолжить ожидание |
| `POST /runs/{id}/partial` | Разрешить неполную сводку |

Предпросмотр — только чтение: не создаёт запусков, задач, уведомлений или аудита.
Его данные предварительны и могут измениться до закрытия окна. Не показываются
секреты каналов, сетевые параметры, внутренние курсоры и ключи операций.

Миграция `0010` добавляет `digest_definitions`, `digest_versions`,
`digest_receipts`, `digest_runs`, `digest_items`. Существующие строки не изменяются.
Внешние ключи сохраняют исходные поступления и состав; правила очистки должны
учитывать эти связи в этапе 11. При откате остановить процессы версии 0.10.0:
таблицы сводок и их история удаляются. Уже подготовленные уведомления остаются
самостоятельными и продолжают обычную доставку версии 0.9.0. Для возврата
истории необходима резервная копия.

## Проверка

```bash
python3 scripts/verify-identity.py --background --ingestion --routing --channels --escalations --digests
```

Временный стенд принимает повторные сообщения межсетевого экрана, формирует
сводку в 08:00 по управляемым часам и отправляет одно письмо локальному
TLS-приёмнику. Основная установка и внешние корпоративные получатели
в этих проверках не используются.

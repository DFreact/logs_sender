# Доставка уведомлений: реализованный контракт этапа 8

## Создание и подготовка

Новое исполнение действия «Отправить уведомление» с выбранным каналом создаёт
уведомление в одной транзакции с обработкой события. Повтор обработки одного
исполнения не создаёт второе уведомление. Старые намерения этапов 6–7 не
переисполняются после обновления. Непривязанные к каналу действия остаются
намерениями. Эскалации исполняются с этапа 9; сводки относятся к этапу 10.

До отправки сохраняются контекст события, название и параметры получателя,
версия шаблона, готовая тема и текст. Важность подставляется по-русски, источник —
его пользовательским названием. Изменение шаблона не меняет подготовленные
уведомления. Только уведомление, которое ещё не удалось подготовить, при ручном
повторе использует исправленный текущий шаблон. Размер результата ограничен
64 КиБ; контекст ограничен 1 МиБ и 256 КиБ на строку. HTML проходит прежнюю очистку.

Режимы: сразу, с задержкой от приёма сообщения и в назначенное время. Просроченное
назначение становится доступно сразу. Планировщик не отправляет раньше `due_at`.

## Попытки и восстановление

PostgreSQL хранит состояние доставки. Redis передаёт только сигнал о готовой
задаче. Отдельный обработчик `delivery` использует собственную очередь;
ожидание сети не занимает обработчик входящих сообщений.

Перед сетевым соединением транзакция сохраняет попытку «Обрабатывается»,
уникальный токен и срок владения уведомлением. Сигнальная задача завершается
в той же транзакции. Отправка выполняется вне транзакции, в отдельном процессе
с пределами времени и ресурсов. Результат принимает только актуальный токен
с неистёкшим сроком. Просроченный исполнитель не может перезаписать новое состояние.

По умолчанию сетевой процесс ограничен 15 секундами, срок владения — 60 секундами;
настройки не допускают срок меньше тайм-аута плюс 15 секунд. При истечении срока
планировщик завершает попытку как «Результат неизвестен» и назначает повтор либо
переводит уведомление в неотправленные. Перезапуск Redis не уничтожает задачи БД.

Нельзя атомарно зафиксировать приём сообщения внешним сервером и результат
в PostgreSQL. После принятия сообщения и потери ответа либо остановки процесса
возможна повторная доставка. Предупреждение сохраняется даже после успешной
следующей попытки. Статус «Отправлено» означает приём каналом, а не прочтение.
HTTP-запросы содержат стабильный `Idempotency-Key`, равный идентификатору
уведомления; получатель может его использовать, но поддержка не предполагается.

## Повторы и остановка

- Временный отказ: новая попытка с задержкой. По умолчанию 30, 120, 600 и
  1800 секунд плюс случайная добавка от 0 до 10 процентов; всего пять попыток.
- Постоянный отказ либо исчерпание попыток: «Ошибка» и раздел
  «Неотправленные уведомления». Это выборка сохранённых уведомлений, не отдельная
  очередь Redis.
- `Retry-After` принимается как число секунд или HTTP-дата, ограничивается часом
  и не сокращает собственную задержку. Telegram дополнительно передаёт
  `parameters.retry_after`. HTTP 429 и 5xx считаются временными ошибками.
- Почтовые ответы 4xx допускают повтор, 5xx — постоянный отказ. Частичный приём
  списка получателей считается неопределённым результатом: повтор может дублировать
  письмо уже принявшим его адресатам.
- Выключенный канал или адаптер приостанавливает очередь без расхода попыток.
  Проверка повторяется через 30 секунд. Скрытие адаптера сохраняет существующую
  доставку. Изменение параметров получателя также приостанавливает старую очередь:
  восстановите параметры либо отмените уведомление и создайте новое событие или
  явную тестовую отправку.
- Замена секрета применяется к следующей попытке без изменения подготовленного
  текста. Номер версии секрета фиксируется в попытке; значение не сохраняется в ней.
- Подавленное событие отменяет ещё не начатую отправку. Начатое соединение нельзя
  гарантированно отозвать. Подтверждение и решение останавливают уведомления эскалации; подавление —
  также обычные уведомления ([контракт этапа 9](event-actions-and-escalation.md)).

Оператор и администратор могут повторить уведомление со статусом «Ошибка».
Начинается новая серия попыток, прежняя история сохраняется. Отменить можно
ожидающее, повторяемое или неотправленное уведомление; отправленное и отменённое
уведомления терминальны. Повтор и отмена требуют версии и ключа операции.
Повтор запроса с тем же ключом, пользователем и содержимым не дублирует действие;
повторное использование ключа с другим содержимым вызывает безопасную ошибку.

Правила трактовки транспорта опираются на
[RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after),
[контракт smtplib](https://docs.python.org/3/library/smtplib.html)
и [параметры ответа Telegram](https://core.telegram.org/bots/api#responseparameters).

## Интерфейс, права и ошибки

Все роли читают список, карточку и историю попыток. Оператор и администратор
повторяют и отменяют; только администратор отправляет тестовое уведомление.
Перед тестом форма явно называет канал и предупреждает о реальной отправке.
Лимит тестовых операций — 10 в минуту на команду. Проверка подключения и
предпросмотр остаются без отправки сообщений.

API не отдаёт секрет, контекст подготовки, параметры подключения, токен владения
или необработанный ответ получателя. В историю попадают только разрешённые коды
причин, которые интерфейс переводит через общий каталог. Неизвестная причина
отображается общей русской ошибкой. Ошибки сети объясняют причину и следующий шаг.
Исходный код HTML в карточке показывается как текст, без выполнения разметки.

## Настройка установки

В Compose доступны `HUB_DELIVERY_RETRY_DELAYS` (JSON-массив, до восьми задержек
по 1–86400 секунд) и `HUB_DELIVERY_JITTER_PERCENT` (0–20). Политика сохраняется
при создании уведомления; ручной повтор берёт текущую политику. После изменения
пересоздайте фоновые процессы и API.

Исходящие имена, сети и порты по-прежнему должны быть явно разрешены.
TLS проверяется всегда, перенаправления запрещены. Для корпоративного центра
сертификации можно смонтировать PEM-файл только для чтения и задать
`HUB_OUTBOUND_CA_FILE` одинаково для API и `delivery` через дополнительный файл
Compose. Файл должен содержать все доверенные корни, нужные установке.
Отключения проверки сертификатов нет.

## Проверка без внешних получателей

```bash
python3 scripts/verify-identity.py --background --ingestion --routing --channels --notifications
```

Команда создаёт отдельный проект с PostgreSQL, локальным TLS-имитатором Telegram
и короткими тестовыми задержками. Проверяется реальный путь SMTP → Kaspersky →
правило → шаблон → доставка, ограничение частоты, постоянный отказ, потеря ответа,
восстановление после остановки Redis, затем права, конкуренция и браузерные
сценарии. Имя Telegram разрешается в адрес локального контейнера только внутри
временного проекта. Основная установка и реальные получатели не используются.

# Отказы и восстановление

Гарантия проектируется как «как минимум один раз» для устойчиво принятых
сообщений. «Ровно один раз» для внешней доставки не обещается.

| Отказ | Поведение | Восстановление |
| --- | --- | --- |
| PostgreSQL недоступен при приёме | SMTP 4xx / HTTP 503, успех не подтверждать | Отправитель повторяет; REST использует ключ идемпотентности |
| Redis недоступен | Сообщения и WorkItem сохраняются в БД, растёт очередь | Диспетчер публикует незавершённые задачи после восстановления |
| Файловое хранилище недоступно/переполнено | Приём не подтверждается, временный файл удаляется позже | Восстановить место/хранилище, повторить приём |
| Сбой после записи blob до транзакции | Возможен файл без владельца | Сборщик сирот после защитного периода |
| Сбой после транзакции до ответа приёма | Отправитель может повторить | REST-идемпотентность; SMTP допускает повтор, помогает объединение |
| Сбой обработки после части вычислений | Транзакция откатывается либо эффект уже зафиксирован | Повтор по WorkItem; уникальные ключи исключают повтор эффекта |
| Сбой после публикации в Redis | Может быть повторная публикация | Потребитель проверяет состояние/аренду задачи в БД |
| SMTP/Telegram/Webhook недоступен | Попытка с безопасным кодом и сроком повтора | Повтор по политике; затем «Неотправленные уведомления» |
| Канал принял сообщение, запись результата не удалась | Результат неизвестен | Возможна повторная доставка; сохранить историю неоднозначности |
| Рестарт планировщика | Сроки и окна не пропадают | Выбор просроченных шагов и окон из БД ограниченными пакетами |
| Рестарт обработчика | Аренда заканчивается | Закрыть незавершённую попытку как UNKNOWN, восстановить задачу |
| Некорректное сообщение/шаблон | Не повторять бесконечно одну постоянную ошибку | Сохранить безопасную причину, дать исправить конфигурацию |

Аренда включает lease_token: устаревший исполнитель не может перезаписать
результат нового владельца. Это защищает БД, но не отменяет уже отправленный
внешний запрос. Тайм-аут внешней операции меньше аренды, длительные операции
продлевают аренду; одновременное исполнение всё равно должно быть безопасным.

SMTP-ответ «принято» и успешный ответ API канала означают принятие следующим
узлом, не прочтение человеком. Для Webhook передавать стабильный идентификатор
уведомления как ключ идемпотентности, если получатель поддерживает его.
Для SMTP/Telegram нельзя рассчитывать на обязательное устранение дублей.

Тестирование отказов включает остановку процессов в каждой границе до/после
фиксации, полную потерю Redis, тайм-аут после внешнего успеха, заполнение диска
и одновременное подтверждение/эскалацию. Приёмка измеряет восстановление,
сохранность и допустимые дубли; метрики и русские сообщения должны объяснять
отказ без раскрытия диагностических подробностей.

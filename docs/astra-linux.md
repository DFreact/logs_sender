# Astra Linux 1.7 и 1.8: перенос и автономная сборка

Целевая архитектура этого комплекта — x86-64. Реальная совместимость
с Astra Linux 1.7 и 1.8 **не подтверждена**. Контейнеры
используют ядро узла: успешный перенос образов сам по себе не проверяет ядро,
libseccomp, cgroups, Docker, файловую систему и мандатные ограничения Astra.

| Среда | Проверка |
| --- | --- |
| Ubuntu 26.04, x86-64, Docker 29.8, Compose 5.5 | Локальные сборка и функциональные проверки |
| Astra Linux 1.7, x86-64 | Не выполнена: нет тестового узла |
| Astra Linux 1.8, x86-64 | Не выполнена: нет тестового узла |
| Другая архитектура | Не входит в подготовленный комплект |

Ограничения контейнеров Astra, включая мандатные уровни и интеграцию Docker,
нужно учитывать по [документации производителя](https://docs.astralinux.ru/latest/guide/virtual/docker/restrictions/).
Не отключать мандатную защиту или seccomp ради успешного запуска. Использовать
одобренные организацией версии Docker и Compose с поддержкой необходимых параметров.

## Два независимых комплекта

Готовые образы: `eventhub-0.12.2-offline.2`, инструкция
[автономной установки](offline-operations.md). Node.js и Python приложения
уже находятся в образах. На узле нужны Docker, Compose, iproute2, Python 3.7+.
Пакеты этих инструментов устанавливаются из доверенного локального репозитория организации.

Исходники с зависимостями: `eventhub-0.12.2-source`.
Подготовка на проверенной машине сборки:

```bash
python3 scripts/prepare-build-kit.py --output /защищённый/путь/исходники
```

Перенести весь каталог, отдельно сверить SHA-256 `build-manifest.json` с доверенным
значением, затем из каталога комплекта:

```bash
python3 build.py
```

Скрипт проверяет состав и суммы файлов, загружает локальные базовые образы,
проверяет идентификаторы и архитектуру. Сборка выполняется без кэша и без сети,
без загрузки pip/npm-пакетов. Результат — отдельные метки `0.12.2-rebuilt`
и `build-result.json`; проверенные рабочие образы не перезаписываются.
Повторный запуск требует нового каталога комплекта. Контрольная сумма не заменяет
проверку происхождения или подпись: инструменты неизвестного комплекта не запускать.

Зависимости подготовлены заранее: точные версии Python-пакетов, снимок npm-зависимостей
с lock-файлом, обновлённые системные библиотеки. Интернет допускается только
на машине подготовки. Изменение requirements или lock-файла требует нового
проверенного комплекта зависимостей; это не универсальная автономная установка любых пакетов.
Подготовка не воспроизводит побайтно исторические репозитории ОС: используются
зафиксированные идентификаторы уже экспортированных образов.

## Проверка целевого узла

`preflight.py --output /tmp/eventhub-preflight.json` собирает версии ОС, ядра,
Docker, Compose, cgroups, настройки защиты и доступное место. Дополнительные
`--backend-image` и `--node-image` принимают локальные метки/идентификаторы образов:
проверяются потоки, Argon2, криптография, блокировки и синхронизация файлов,
Node.js worker threads. Контейнеры запускаются без сети, без дополнительных
привилегий и с корневой файловой системой только для чтения.

Для каждой версии Astra отдельно остаётся выполнить:

1. Загрузку и автономную сборку в условиях физически закрытого Интернета.
2. Запуск всех компонентов и миграции на пустых томах при штатной защите Astra.
3. Приём REST/SMTP, работу интерфейса и отправку в тестовый чат MAX с реальным токеном.
4. Положительные и отрицательные сетевые пробы, включая DNS/IPv6 и перезагрузку узла.
5. Резервную копию и восстановление в отдельную установку.
6. Длительный прогон на согласованной нагрузке и контроль ресурсов.

До выполнения этих пунктов комплект — кандидат для испытаний, а не подтверждённый
промышленный выпуск для Astra. Не включать в акт приёмки результаты Ubuntu вместо Astra.

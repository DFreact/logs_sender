# Приём и просмотр событий: реализованный контракт

Контракт приёма введён на этапе 4. SMTP и REST сохраняют
исходное сообщение, затем отдельный обработчик определяет источник и создаёт
или дополняет событие. Каждое новое поступление
создаёт отдельное событие, если объединение повторов выключено.
На этапе 5 добавлены [определение источника](source-identification.md)
и [объединение повторов](deduplication.md).
На этапе 6 добавлены [правила обработки](routing-and-simulation.md).

## Надёжность и данные

Миграция `0004` добавляет `adapter_installations`, `ingest_credentials`,
`raw_messages`, `attachments`, `events`, `event_occurrences`.
Получатель резервирует метаданные файла, записывает временный файл, выполняет
`fsync`, переименование и `fsync` каталога. Затем одной транзакцией создаются
RawMessage, ссылка на готовый файл и WorkItem NORMALIZE. Только после commit
выдаются SMTP 250 или REST 202. Отказ диска/БД не даёт успешного подтверждения.
При потере ответа после commit SMTP может доставить повтор; это нормальная
неоднозначность протокола. Message-ID не является уникальным ключом.

Оптимизация приёма сохраняет резерв файла в транзакции предварительной проверки.
После её успешного завершения выполняется запись файла без открытой транзакции БД.
Размер и контрольная сумма передаются из успешного `BlobStore.write` в финальную
транзакцию: метаданные, состояние READY, исходное сообщение и задача нормализации
фиксируются вместе. Промежуточная транзакция только для размера/контрольной суммы
не нужна. Обычный новый REST-запрос использует три транзакции вместо пяти, SMTP —
две вместо четырёх; повторы с ключом идемпотентности могут завершиться раньше.

Предварительная и финальная транзакции берут блокировку команды раньше блокировок
ключа и адаптера — в том же порядке, что административные операции. Это также
защищает от взаимной блокировки при проверке внешнего ключа резерва файла.
Финальная транзакция повторно проверяет ключ и адаптер и блокирует резерв файла.
Если очистка уже перевела резерв в удаление, приём завершается ошибкой; вернуть
такой файл в READY нельзя. Сбой после записи файла оставляет STAGING без владельца,
размера и контрольной суммы; действующая очистка удаляет его после защитного срока.
Сохранение вложений при нормализации продолжает использовать прежний `stage`.

Redis не участвует в подтверждении приёма. Очередь `ingestion` и отдельный
процесс `ingestion` выполняют нормализацию; `maintenance` обслуживает файлы.
Аренды, повторная публикация и восстановление — из этапа 3. До 20 попыток
обработки, затем задача остаётся FAILED, что видно администратору в состоянии
системы. Исходное сообщение сохраняется. Автоматическая повторная обработка
после исчерпания попыток и управление такими задачами в интерфейсе пока отсутствуют.

Запись события, единственного поступления, ссылок на вложения и завершение
задачи фиксируются вместе с проверкой аренды. Неудача транзакции оставляет
исходное сообщение для повторной обработки; временные вложения собирает очистка.
Уникальная ссылка EventOccurrence → RawMessage защищает от повторного эффекта.
Подготовленные файлы могут оставаться после сбоя до истечения защитного периода.
Сроки хранения подтверждённых сообщений будут реализованы на этапе 11.

## REST

`POST /api/v1/ingest` с `Authorization: Bearer <ключ>` принимает произвольный
JSON, включая массивы и скаляры, либо UTF-8 текст. Content-Type — `application/json`
или `text/plain`; допустим `charset=utf-8`. Сжатие запроса не поддерживается.
Схема Event не требуется. Если JSON-объект содержит subject, sender, body,
severity, они используются для предварительного отображения; неизвестная важность
не назначается. Остальные поля доступны в оригинале. Это начальное отображение,
не правило определения источника или обработки.

Ответ 202: `{"receipt_id":"UUID"}`. Необязательный `Idempotency-Key` — 1–128
печатных ASCII-символов без пробелов. Область ключа — конкретный ключ приёма,
привязанный к команде. Повтор того же тела и типа возвращает прежнюю квитанцию;
другое тело/тип — 409. Без ключа каждый POST создаёт новое поступление. В БД
сохраняется хеш ключа идемпотентности, а не его исходное значение.

`GET /api/v1/ingest/{receipt_id}` с тем же ключом возвращает состояние задачи
и event_id после обработки. Чужая квитанция недоступна. Ключ приёма не разрешает
доступ к пользовательскому API, скачивание файлов или администрирование.

Ключи генерируются из 32 случайных байтов, хранятся как SHA-256, действуют 90 дней.
Создание и отзыв доступны оператору установки в интерактивной локальной консоли:

```bash
docker compose -p eventhub-dev -f infra/compose/compose.yaml exec api python -m app.ingest_cli create --name 'Система резервного копирования'
docker compose -p eventhub-dev -f infra/compose/compose.yaml exec api python -m app.ingest_cli list
docker compose -p eventhub-dev -f infra/compose/compose.yaml exec api python -m app.ingest_cli revoke --id UUID
```

Создание выводит идентификатор и сам ключ один раз. Сохранить ключ в защищённой
конфигурации отправителя. Не помещать ключ в URL, командную строку или журналы.
Список не показывает ключи и хеши. Действия фиксируются в журнале аудита как
локальные операции установки. В актуальном исходном коде управление ключами также доступно администратору
в разделе «Подключение источников»: создание, однократный показ, срок действия
и отзыв с подтверждением. Контракт описан ниже.

## SMTP

Локальный стенд слушает только `127.0.0.1:2525`; разрешён получатель
`events@localhost`. Порт изменяется через `HUB_SMTP_PORT`. Он не пересылает письма
на внешние адреса. Список получателей и сети задаются настройками процесса.
Допускается пустой отправитель конверта; адрес заголовка From хранится отдельно.

| Настройка процесса | Значение по умолчанию |
| --- | --- |
| HUB_SMTP_HOST / HUB_SMTP_PORT | 127.0.0.1 / 2525 |
| HUB_SMTP_ALLOWED_NETWORKS | `["127.0.0.0/8","::1/128"]` |
| HUB_SMTP_RECIPIENTS | `["events@localhost"]` |
| HUB_SMTP_MAX_RECIPIENTS | 10 |
| HUB_SMTP_MAX_CONNECTIONS | 20 |
| HUB_SMTP_ALLOW_PLAINTEXT | false |
| HUB_SMTP_TLS_CERT / HUB_SMTP_TLS_KEY | пути к сертификату и ключу |

В Compose явно разрешён незашифрованный SMTP для локального стенда, разрешена
его внутренняя Docker-подсеть и опубликован только loopback-порт. Для сетевой
установки нужен отдельный конфигурационный файл Compose: доверенные сети,
разрешённые получатели, read-only монтирование сертификата/ключа, STARTTLS
с TLS 1.2+ и `HUB_SMTP_ALLOW_PLAINTEXT=false`. Без сертификата защищённый
получатель не запускается. SMTP AUTH не реализован: доступ ограничивают сети
и получатели; открывать такой приёмник для недоверенной сети нельзя.

Используется aiosmtpd 1.4.6; проверен на Python 3.14.4. Параметры размера,
STARTTLS, тайм-аутов и команд взяты из [официального контракта SMTP](https://aiosmtpd.aio-libs.org/en/stable/smtp.html).
Не более 100 команд на соединение, тайм-аут бездействия 60 секунд. Неподходящая
сеть или исчерпание соединений — 421; чужой получатель — 550;
временный отказ сохранения/лимит частоты — 451.

## Ограничения и разбор

| Ограничение | Значение |
| --- | --- |
| HUB_INGEST_MAX_BYTES | 1 МиБ на запрос/письмо; также ограничивается HUB_BLOB_MAX_BYTES |
| Nginx client_max_body_size | 1 МиБ; при изменении лимита согласовать обе настройки |
| HUB_INGEST_PER_MINUTE | 120 на ключ REST; 120 суммарно на SMTP-процесс |
| JSON | глубина 20, не более 10 000 узлов; без NaN/Infinity |
| MIME | до 100 частей, глубина 20, до 25 МиБ декодированных данных |
| Предварительная проверка MIME | до 200 строк границ/Content-Type; консервативное ограничение |
| Текст просмотра | до 65 536 символов |
| Заголовки в нормализованной записи | до 100, значения до 1000 символов |

Лимит REST атомарен и хранится в БД отдельно для каждого ключа; проверяется
до чтения тела. Лимит SMTP действует в одном процессе и сбрасывается при его
перезапуске. Ограничения защищают MVP; нагрузочная аттестация — этап 12.

Повреждённый MIME сохраняется целиком, а частичный разбор помечается LIMITED.
Нормальный результат — NORMALIZED; до обработки — PENDING. Эти значения
внутренние. В интерфейсе частичный разбор сопровождается русским пояснением.
HTML преобразуется в текст, скрипты и стили исключаются; внешний контент
не загружается. Предпросмотр не использует dangerouslySetInnerHTML или iframe.
Оригинал сохраняет все исходные данные, в том числе пропущенные при просмотре.
Вложенные письма доступны как вложения; их MIME-представление может быть
пересобрано библиотекой, побайтовый оригинал находится в исходном сообщении.

## События и доступ к файлам

Все три роли читают `/api/v1/events` и `/api/v1/events/{id}` в своей команде.
Список поддерживает q (тема/отправитель), status, severity, adapter, received_from,
received_to (ISO 8601 с часовым поясом), offset/limit. Предел страницы — 100,
интерфейс использует 25. Даты фильтров вводятся в часовом поясе устройства.
Карточка показывает содержимое, важность, статус, отправителя, неопределённый
источник и историю поступлений. Сейчас у события одно поступление.

Скачивание: `/{event_id}/raw/{raw_id}` и `/{event_id}/attachments/{attachment_id}`
под `/api/v1/events`. Проверяются сеанс, команда и связь с конкретным событием;
ключ приёма не подходит. Отдаются application/octet-stream, attachment,
nosniff и запрет активного содержимого. Файловые пути и хеши не возвращаются.
Имена вложений очищаются от путей и управляющих символов, но не используются
в качестве пути на диске. В браузере вложение сохраняется как «вложение.bin»;
исходное отображаемое имя остаётся в карточке.

## Подключение источников через интерфейс

Доработка после кандидата 0.12.1: отдельный пункт «Подключение источников»
и ссылка со страницы «Источники». Раздел доступен только администратору.
В нём показаны адрес REST, метод и заголовок авторизации, пример JSON,
размер сообщения, частота запросов, квитанция и защита от повторов;
для SMTP — опубликованный сервер, порт, получатели и режим шифрования.

Адрес REST строится по адресу открытого приложения; браузер явно поясняет,
что loopback недоступен с другой машины. Адрес SMTP задаётся установщиком:
`HUB_SMTP_PUBLIC_HOST` и `HUB_SMTP_PUBLIC_PORT`. Отсутствие имени не подменяется
адресом контейнера: интерфейс просит опубликовать параметры. Это описание
установки, а не доказательство доступности порта. `HUB_SMTP_RECIPIENTS` и
`HUB_SMTP_ALLOW_PLAINTEXT` должны совпадать у API и почтового приёмника.
В Compose они вынесены в общую конфигурацию; публикуемый порт берётся из
`HUB_SMTP_PORT`. Стандартный Compose по-прежнему публикует порт только на
127.0.0.1. Сетевой приём требует отдельной настройки публикации, разрешённых
сетей и сертификатов; ввод адреса в описание сам по себе не открывает порт.

Маршруты требуют `MANAGE_CONFIGURATION`, изменяющие запросы — также Origin/CSRF:

- `GET /api/v1/connections` — безопасные параметры подключения;
- `GET /api/v1/connections/keys?offset=0` — 25 записей и `has_more`;
- `POST /api/v1/connections/keys` с `name` — ключ на 90 дней;
- `POST /api/v1/connections/keys/{id}/revoke` — идемпотентный отзыв.

Токен возвращается только при создании, с `Cache-Control: no-store`. В БД
остаётся хеш. В браузере токен находится только в состоянии компонента до
скрытия или ухода со страницы, без localStorage/sessionStorage. Потерянный
ответ не позволяет восстановить токен: обновить список, отозвать созданный
ключ и выпустить новый. Действия аудируются без токенов и хешей.
На команду допускается 1000 действующих ключей. Ошибка при превышении прямо
предлагает отозвать неиспользуемый ключ. Отозванные записи сохраняют историю.

Замена: создать новый ключ → обновить отправителя → проверить приём →
отозвать старый. Область Idempotency-Key привязана к ключу приёма: дублирование
одного сообщения между старым и новым ключами не устраняется автоматически.
Имя ключа не определяет источник и не создаёт изоляцию компании; источник
назначается правилами определения источника. Полная изоляция компаний остаётся
отдельной незавершённой задачей.

# ADR-001. Фоновые задачи, Redis и планировщик

Статус: принято и реализовано на этапе 3. Детали контрактов и ограничения —
[background-processing.md](../background-processing.md).

## Сравнение обработчиков

| Вариант | Применимость | Недостатки для проекта |
| --- | --- | --- |
| Celery | Богатая маршрутизация задач, развитые средства эксплуатации | Больше параметров и эксплуатационных соглашений для небольшой команды |
| Dramatiq | Небольшой интерфейс задач, Redis, удобен для отдельных обработчиков | Долговечные бизнес-расписания и их состояния всё равно нужно проектировать |
| ARQ | Естественный asyncio для асинхронных сетевых операций | Требует единого подхода к async и Redis; длительные бизнес-процессы не исчезают из модели БД |

Рекомендация: Dramatiq с Redis как транспортом и PostgreSQL WorkItem как
источником истины. Приоритет — понятная эксплуатация и восстанавливаемость.
Это проектный выбор, а не утверждение о превосходстве в производительности.
Официальная документация [Dramatiq](https://dramatiq.io/best_practices.html)
предупреждает о повторном исполнении; [ARQ](https://arq-docs.helpmanual.io/)
также описывает повторный запуск прерванных задач. Идемпотентность нужна
независимо от выбора. [Celery](https://docs.celeryq.dev/en/stable/userguide/tasks.html)
предоставляет настройки подтверждения задач, но они не заменяют бизнес-транзакции.

## Решения и пути изменения

| Область | Рекомендация и причина | Альтернатива и недостаток | Будущая миграция |
| --- | --- | --- | --- |
| Брокер | Redis для быстрого пробуждения обработчиков; задачи восстановимы из БД | RabbitMQ добавляет отдельную компетенцию; только БД увеличивает опрос | Меняется диспетчер/транспорт, бизнес-задачи сохраняют идентификаторы |
| Планировщик | Процесс с коротким опросом сроков БД, блокировками и уникальными ключами | Таймеры в памяти теряют сроки; cron не хранит состояние окна | Несколько экземпляров с общей блокировкой; внешний планировщик через те же команды |
| Повторы | due_at, число попыток и политика в БД, единый владелец бизнес-повторов | Одновременно встроенные повторы брокера и бизнес-повторы умножают отправки | Менять алгоритм политики с её версией, не теряя историю |
| Неотправленные уведомления | Логическое представление FAILED/dead_lettered_at | Отдельная очередь копирует данные и усложняет согласование | Отдельное хранилище только при доказанной нагрузке, с сохранением идентификаторов |

Встроенные транспортные повторы допустимы только для пробуждения WorkItem;
они не должны напрямую обходить проверку due_at, аренды и лимита попыток.
Цена решения — дополнительный диспетчер и таблица задач. Восстановление после потери Redis и повторной публикации проверяется
сценариями этапа 3.

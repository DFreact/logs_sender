# Перенос локального стенда с 0.11.0 на 0.12.2

Инструмент переносит согласованную копию в **новые** проект Docker и тома.
Он не меняет владельцев объектов в работающей старой БД и не выполняет
миграции над исходными томами. Поддерживается только переход с копии
`0.11.0-offline.1`, схемы `0011`, на `0.12.2-offline.1`, схему `0012`.
Восстановление копии той же версии остаётся отдельной командой `admin.py restore`.

## Согласованная копия старого локального проекта

`scripts/snapshot-legacy.py` предназначен только для `eventhub-dev` этого
рабочего каталога: проверяет метки контейнеров, образ API 0.11.0 и схему 0011.
Перед копированием останавливает все восемь компонентов, изменяющих данные.
PostgreSQL и Redis остаются доступны для обслуживания. Экспортируются дамп,
файлы, ключ каналов и разрешённые рабочие настройки без паролей.
Сверяются 44 таблицы; контрольные суммы файлов и манифест записываются последними.
Для сверки таблиц используются количество строк и две суммы половин MD5 строк,
без экспорта содержимого и без накопления всех строк в памяти. Это проверка
целостности переноса, а не криптографическая подпись данных; файлы копии защищены SHA-256.

```bash
.venv/bin/python scripts/snapshot-legacy.py --output .local/backups/rehearsal
```

В обычном режиме исходные компоненты возобновляются с проверкой готовности.
При окончательном переключении используют `--keep-stopped`: новые поступления
между точкой копии и переключением не принимаются. При сбое создания копии
инструмент пытается восстановить прежнюю работу. Неполную копию без манифеста
использовать нельзя. Каталоги копий имеют права 0700, файлы создаются с маской 077.

## Пробный перенос

```bash
python3 .local/releases/0.12.2-offline.1/upgrade.py \
  --backup .local/backups/rehearsal --directory .local/rehearsal \
  --project eventhub-rehearsal --http-port 8086 --smtp-port 2531 \
  --subnet 172.31.60.0/24 --isolated
python3 .local/releases/0.12.2-offline.1/admin.py start --directory .local/rehearsal
```

Сначала проверяются контрольные суммы копии, поддерживаемый переход и отсутствие
целевых ресурсов. Затем создаются новые пароли и роли PostgreSQL. Дамп импортируется
одной транзакцией под ролью миграций, без переноса старых владельцев и разрешений.
До миграции проверяются схема и отпечатки таблиц; после миграции они сверяются снова.
Схема обновляется до 0012, назначаются права приложения и будущих объектов.
Проверяются размер и SHA-256 сохранённых файлов и расшифровка секретов каналов.
Учётные записи и пароли пользователей сохраняются, прежние сеансы отзываются.
Ключ шифрования каналов сохраняется; остальные системные секреты создаются заново.

При ошибке новая установка остаётся неготовой, прикладные компоненты не запускаются.
Исходная установка не меняется. Не помечать установку готовой вручную.

## Локальный доступ без выхода в интернет

В режиме `--isolated` все контейнеры находятся в одной внутренней сети Docker,
без IPv6 и внешнего DNS. У веб-сервера и SMTP закреплены адреса `подсеть+12`
и `подсеть+13`, динамический диапазон вынесен во вторую половину подсети.
Публикация портов Docker для такой сети не используется.

Для локального Ubuntu-стенда `scripts/local-access.py` создаёт пользовательские
модули systemd, которые слушают **только 127.0.0.1** и пересылают соединения
на два фиксированных внутренних адреса. Модули используют установленный
`/usr/lib/systemd/systemd-socket-proxyd`, без привилегий администратора ОС.
Они не являются HTTP-прокси общего назначения и не принимают адрес назначения
от клиента. Сетевой доступ контейнеров наружу не открывается.

```bash
python3 scripts/local-access.py --directory .local/rehearsal \
  --label eventhub-rehearsal --http-port 8086 --smtp-port 2531
systemctl --user link "$PWD"/.local/rehearsal/local-access/*.service
systemctl --user enable --now "$PWD"/.local/rehearsal/local-access/*.socket
```

Это локальный режим, а не промышленная публикация в корпоративной сети.
При `Linger=no` пользовательские модули доступны после входа пользователя ОС;
автономный запуск до входа требует настройки администратором ОС. На Astra этот
способ доступа не проверялся. Штатный промышленный профиль использует проверенные
правила межсетевого экрана и публикацию через корпоративный HTTPS-прокси.
Для перехода из изоляции восстановить копию текущей версии в новую установку
с заранее применённым сетевым профилем, а не снимать ограничения на месте.

## Переключение и возврат

Перед переключением должны пройти пробный перенос, вход сохранённого администратора,
проверки ролей БД/секретов, нового интерфейса и приёма. Снять свежую копию старого
проекта с `--keep-stopped`, восстановить её в новый проект и проверить готовность
до открытия локальных сокетов 8080/2525. Только после этого направить локальный
доступ на новую установку. Старые контейнеры и тома сохранить остановленными.

До открытия новой установки можно вернуться простым запуском сохранённых старых
контейнеров. После начала приёма новых данных такой возврат **потеряет новые
поступления**: нужно сначала остановить приём, снять копию новой установки и
согласовать перенос данных. Схему 0012 нельзя автоматически понижать поверх
новых данных. Старый Compose из текущих исходников над старыми томами не запускать.

Проверки: `scripts/verify-upgrade.py`, `frontend/scripts/verify-upgrade.mjs`.
Первый проверяет фактические права БД, наборы секретов, отсутствие внешнего
маршрута, доступ администратора и API; `--exercise` дополнительно принимает
тестовые REST/SMTP-события, поэтому применяется к пробной копии. Второй выполняет
вход в браузере, проверяет новые разделы и узкий экран, фиксирует отсутствие
внешних запросов и выходит из аккаунта. Пароли в отчёты не попадают.
